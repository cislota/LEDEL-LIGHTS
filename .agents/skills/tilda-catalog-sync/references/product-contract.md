# Контракт синхронизации товаров с Tilda

Этот документ описывает текущий путь данных от Tilda Store API до таблицы `products` в PostgreSQL. Он используется вместе с `../SKILL.md` при изменении загрузки, нормализации и сохранения товаров.

Источники реализации:

- `backend/services/tilda_sync.py` — запрос к Tilda, нормализация, категоризация и upsert;
- `backend/models/product.py` — модель `Product`;
- `backend/models/sync_log.py` — модель `SyncLog`;
- `backend/schemas.py` — публичные Pydantic-схемы товаров и журналов синхронизации;
- актуальные миграции из `backend/alembic/`.

Если документ расходится с кодом или миграциями, не выбирай одну из версий молча. Зафиксируй расхождение и обнови контракт вместе с изменением реализации.

## Запрос к Tilda Store API

Синхронизация выполняет HTTP-запрос к адресу из `TILDA_API_URL`. Значения параметров подключения берутся из конфигурации окружения и не должны находиться непосредственно в коде.

| Параметр | Источник | Назначение |
| --- | --- | --- |
| `storepartuid` | `TILDA_STORE_PART_UID` | Идентификатор части каталога Tilda |
| `recid` | `TILDA_RECID` | Идентификатор блока магазина |
| `slice` | Счётчик страниц, начиная с `1` | Номер загружаемой части каталога |

Для каждого запроса используется тайм-аут 30 секунд. Ошибки соединения, HTTP-ошибки и ошибки разбора ответа должны попадать в журнал приложения без вывода учётных данных и полного production-ответа.

## Структура ответа Tilda

Сервис использует следующие поля верхнего уровня:

| Поле | Ожидаемый тип | Использование |
| --- | --- | --- |
| `status` | строка | Значение `OK` означает успешный ответ |
| `products` | массив | Товары текущей страницы |
| `total` | число | Общее количество товаров по данным Tilda |
| `nextslice` | значение или `null` | Признак наличия следующей страницы |

Загрузка завершается, когда `products` пуст либо в ответе отсутствует `nextslice`.

## Преобразование товара

| Поле Tilda | Поле `Product` | Правило преобразования |
| --- | --- | --- |
| `uid` | `uid`, `tilda_id` | Приводится к строке и используется как внешний идентификатор товара |
| `recid` | `recid` | Приводится к строке |
| `title` | `title` | Сохраняется как название товара |
| `title` | `name_main` | Часть названия до первого символа `/` |
| `title` | `name_spec` | Часть названия после первого символа `/` |
| `title` | `slug` | Транслитерация, нижний регистр, дефисы; длина до 200 символов |
| `descr` | `description` | Краткое описание; сохраняются первые 500 символов |
| `text` | `text` | Полное описание товара |
| `price` | `price` | Числовое значение преобразуется в `float`; пустое значение сохраняется как `null` |
| `currency` | `currency` | Если поле отсутствует, используется `RUB` |
| `gallery` | `gallery` | JSON-строка разбирается и сохраняется как JSON-строка |
| `gallery` | `image_url` | Используется первое доступное значение `img`, `url` или `1080` |
| `characteristics` | `specs` | Массив сохраняется как JSON-строка |
| `type` | `type` | Тип товара без дополнительного преобразования |
| `sku` или `article` | `article` | Сначала используется `sku`, затем `article` |
| `brand` | `brand` | Бренд без дополнительного преобразования |
| `is_available` | `is_available` | По умолчанию `true` |
| `is_visible` | `is_visible` | По умолчанию `true` |
| `quantity` | `stock` | Приводится к целому числу; некорректное или пустое значение заменяется на `0` |

Поле `descr` не используется для определения категории: в текущих данных оно содержит обозначения наподобие «Проектор» или «Светильник», а не категорию каталога.

## Определение категории

Категория вычисляется по основной части `title` без учёта регистра.

| Фрагмент названия | Категория |
| --- | --- |
| `L-street` | Уличное освещение |
| `L-office`, `L-fusion office` | Офисное освещение |
| `L-fusion retail` | Коммерческое освещение |
| `L-contour`, `L-facade` | Архитектурно-парковое освещение |
| Другие значения | Промышленное освещение |

При изменении правил категоризации необходимо проверить согласованность backend-логики с отображением и фильтрацией категорий во frontend.

## Идентификация и upsert

Внешним идентификатором товара является `uid` из Tilda. При нормализации одно и то же значение записывается в `Product.uid` и `Product.tilda_id`.

Перед созданием товара выполняется поиск записи, у которой совпадает `uid` или `tilda_id`:

- если запись найдена, её поля обновляются, а `updated_at` и `last_synced_at` получают текущее время;
- если запись не найдена, создаётся новый `Product`;
- повторная обработка одного и того же `uid` не должна создавать дополнительную запись.

Товар без `uid` не имеет устойчивого внешнего идентификатора. Не выполняй для него upsert и не меняй правило идентификации без отдельного требования, миграции данных и проверки обратной совместимости.

В текущей модели `uid` допускает `null`, а `parse_product` отдельно не отклоняет такой товар. Это известная граница реализации: при изменении upsert необходимо явно проверить товар без `uid` и не считать существующее поведение гарантированной частью контракта.

## Ошибки и границы транзакции

Текущая реализация обрабатывает товары последовательно и фиксирует изменения в базе после каждого товара. Ошибка одного товара увеличивает `failed`; обработка остальных товаров продолжается, если состояние сессии базы данных позволяет это сделать.

Из этого следуют ограничения текущего контракта:

- синхронизация не является одной общей атомарной транзакцией;
- уже сохранённые товары не откатываются при ошибке следующего товара;
- изменение транзакционной модели требует отдельной задачи и проверки поведения при частичной ошибке;
- некорректный товар не должен повреждать ранее сохранённые записи.

Также учитывай два текущих способа обработки пограничных значений:

- если `gallery` не разбирается как JSON, сервис записывает предупреждение и сохраняет исходную строку;
- значение `price`, равное `0`, текущая реализация преобразует в `null`, поскольку проверяет значение как логическое.

Не меняй эти правила попутно с несвязанной задачей. Если они влияют на требуемое поведение, укажи это как отдельное изменение контракта.

## Журнал синхронизации

После завершения создаётся запись в `sync_logs` со следующими значениями:

| Поле | Значение |
| --- | --- |
| `sync_type` | `products` |
| `status` | `success`, `partial` или `error` |
| `items_processed` | Значение `total`, полученное от Tilda |
| `items_created` | Количество созданных товаров |
| `items_updated` | Количество обновлённых товаров |
| `items_failed` | Количество товаров, завершившихся ошибкой |
| `error_message` | Сводное сообщение при частичной или полной ошибке |
| `started_at`, `completed_at` | Время начала и завершения операции |

Статус определяется так:

- `success` — ошибок нет и `total` больше нуля;
- `partial` — обработана только часть товаров;
- `error` — не удалось обработать ни одного товара либо Tilda не вернула товары.

Результат `sync_all_products` содержит `status`, `stats`, `duration_seconds`, `log_id`, `started_at` и `completed_at`.

## Тестовая фикстура

Для локальной проверки используй обезличенный пример ответа, содержащий только вымышленные значения:

```json
{
  "status": "OK",
  "total": 1,
  "nextslice": null,
  "products": [
    {
      "uid": 100001,
      "recid": 200001,
      "title": "L-street Test / 100 W",
      "descr": "Светильник",
      "text": "Тестовое описание",
      "price": null,
      "currency": "RUB",
      "gallery": "[{\"img\": \"https://example.invalid/image.jpg\"}]",
      "characteristics": [
        {"title": "Мощность", "value": "100 Вт"}
      ],
      "brand": "TEST",
      "quantity": 1,
      "is_available": true,
      "is_visible": true
    }
  ]
}
```

Фикстура не должна содержать реальные идентификаторы магазина, production-адреса изображений, токены или полный ответ Tilda.

## Изменение контракта

Изменением контракта считается:

- новое правило идентификации товара;
- добавление, удаление или переименование сохраняемого поля;
- изменение логики нормализации или категоризации;
- изменение публичной Pydantic-схемы;
- изменение структуры таблиц `products` или `sync_logs`;
- изменение семантики статусов и статистики синхронизации.

При таком изменении одновременно проверь сервис синхронизации, модели SQLAlchemy, Pydantic-схемы, миграции Alembic, API и этот документ.
