# Синхронизация каталога Tilda

Следуй явному требованию пользователя. Этот skill задаёт правила проекта для изменений в контуре синхронизации и не расширяет задачу за его пределы.

## Контекст

Перед изменением прочитай [`references/product-contract.md`](references/product-contract.md). Используй его для правил преобразования полей, идентификации товара, категоризации, журналирования и обработки пограничных значений.

Дополнительно открывай только файлы, относящиеся к текущей задаче:

- `backend/services/tilda_sync.py` — загрузка, нормализация и upsert;
- `backend/models/product.py` — таблица `products`;
- `backend/models/sync_log.py` — таблица `sync_logs`;
- `backend/schemas.py` — публичные схемы API;
- `backend/routers/products.py` и связанный маршрут синхронизации — HTTP-контракт;
- актуальные ревизии в `backend/alembic/` — только при изменении схемы базы данных;
- `backend/config.py` — параметры интеграции без значений секретов.

Если код, миграции и `product-contract.md` расходятся, зафиксируй расхождение. Не выбирай одну из версий молча.

## Границы изменения

- Используй существующее правило идентификации товара по `uid` и `tilda_id`, если задача явно не требует его изменить.
- Повторная синхронизация одной фикстуры не должна создавать дубликаты.
- Не переноси логику синхронизации в router.
- Не меняй публичные маршруты и формат ответа без явного изменения API-контракта.
- Не добавляй поля Tilda, которых нет в текущем коде, контракте или обезличенной фикстуре.
- Не сохраняй учётные данные и необработанные production-ответы в коде, фикстурах и журналах.
- Выполняй изменение схемы базы данных только через Alembic.
- Не исправляй попутно известные пограничные случаи из `product-contract.md`, если они не относятся к задаче.

## Порядок работы

1. Восстанови только затрагиваемый участок потока данных: ответ Tilda → разбор → нормализация → категоризация → upsert → `sync_logs`.
2. До правок определи, меняются ли контракт Tilda, публичный API, модели SQLAlchemy, Pydantic-схемы или структура базы данных.
3. Внеси минимальное изменение, необходимое для требуемого поведения.
4. При изменении контракта обнови `references/product-contract.md` вместе с кодом и миграциями.
5. Проверь итоговый diff: в нём не должно быть несвязанных файлов, секретов, кешей, результатов сборки и сырых production-данных.

Если недостающая информация может привести к потере данных, дубликатам или несовместимому изменению API, запроси уточнение. В остальных случаях явно укажи принятое допущение и продолжай работу.

## Проверка

Для изменения логики синхронизации используй обезличенную локальную фикстуру и проверь:

- повторный запуск не создаёт новый товар с тем же `uid`;
- изменённые данные существующего товара обновляются;
- некорректный товар обрабатывается контролируемо и не повреждает ранее сохранённые записи;
- статистика и статус операции записываются в `sync_logs`;
- backend собирается и запускается;
- `GET /api/health` отвечает успешно.

При изменении базы данных дополнительно проверь применение миграций Alembic. Выполни подходящие команды из корневого `AGENTS.md` и не объявляй непроведённую проверку успешной.
